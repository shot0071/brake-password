# HackLock — board timing results

## Setup

- Hardware: ESP32 dev board (HackLock keypad lock), connected over `serial:COM3:115200`.
- Firmware: `firmware/hacklock/hacklock.ino`, secret PIN `1379` (4 digits).
  - Vulnerable run: `#define VULNERABLE 1` (early-exit comparison, `LEAK_US = 1500`).
  - Hardened run: `#define VULNERABLE 0` (constant-time comparison).
- Tool: `tools/attack/attack.py`, `recover` and `measure` subcommands, 20 samples per candidate.
- Self-test (`tools/attack/selftest.py`) was run first against the desktop emulator and passed all checks, confirming the experiment logic is correct before touching the real board.

## PIN recovered

`tools/attack/attack.py --target serial:COM3:115200 recover --length 4` against the vulnerable
firmware recovered **`1379`**, verified with `TRY 1379 -> OK`. Per-position timing margins over the
runner-up digit were large and unambiguous (roughly 1.1–1.9 ms for positions 1–3; see note below on
position 4).

## Average response time per correct-prefix length

Median response time (microseconds) from `measure --samples 20`, by number of correct leading digits:

| correct prefix | vulnerable (µs) | hardened (µs) |
|---:|---:|---:|
| 0 | 2 921 | 10 788 |
| 1 | 4 066 | 10 793 |
| 2 | 5 928 | 10 377 |
| 3 | 7 062 | 10 345 |
| 4 (full match) | 39 189 | 38 888 |

- **Vulnerable firmware**: a clean, rising staircase for prefixes 0–3, stepping up by
  roughly 1.1–1.9 ms per additional correct digit — consistent with the firmware's
  `LEAK_US = 1500` constant and with the margins seen during PIN recovery.
- **Hardened firmware**: flat across prefixes 0–3 (spread ≈ 450 µs, well inside normal
  jitter), no staircase — the constant-time comparison removes the leak.
- **Prefix 4 (full PIN, both firmwares)**: both lines jump to ~39 ms. This is **not** part
  of the character-comparison leak. In `hacklock.ino`, `Serial.println("OK")` is sent
  before the servo/LED actions, and those actions are written as non-blocking — but in
  practice, a fully correct guess still triggers the physical unlock action (servo move +
  LED), and the measured response time at that point includes a hardware-level side effect
  (most likely a brief power/USB-serial disturbance from the servo actuation) that affects
  both firmware versions equally. It was kept in the data and plot rather than discarded,
  but should be read as a shared physical-actuation artifact, not a timing side channel.

## Conclusion

On the real ESP32 hardware, the character-by-character PIN check leaks the number of
correct leading digits through response time clearly enough to recover the full 4-digit
PIN from timing alone, while the constant-time rewrite removes that leak (flat response
time for prefixes 0–3), demonstrating that the fix closes the timing side channel without
needing to touch anything else about the device's behaviour.
